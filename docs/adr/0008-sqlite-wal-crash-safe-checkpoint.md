# ADR-008: SQLite WAL ونموذج المتانة ثنائي المستوى (Two-Tier Crash-Safe Durability)

- **Status:** Accepted
- **Date:** 2026-11-25

## Context
لضمان استكمال 100% خالٍ من التلف، لا يجوز أن يسجل SQLite بايتات لم تُحفظ على القرص. لكن استدعاء `FlushFileBuffers` كل ثانيتين أو كل 32 MiB على خط 1–10 Gbps يعني تفريغ كاش القرص الفيزيائي عشرات المرات في الدقيقة، مما يخنق الأداء ويهلك أقراص SSD دون مبرر لأن **OS Kernel Page Cache يعيش أصلاً بعد تعطل البرنامج أو `kill -9`**.

## Decision Drivers
- استحالة إنتاج ملف تالف بعد أي انقطاع كهرباء أو BSOD أو `kill -9` (100% Corruption-Free).
- عدم خنق سرعات 1–10 Gbps والحفاظ على عمر الـ SSD.

## Considered Options
1. **SQLite 3 (WAL mode) + متانة ثنائية المستوى:**
   - **ضد انهيار العملية (`kill -9`):** البايتات المكتوبة عبر `WriteFile` محفوظة في OS Page Cache.
   - **ضد انقطاع الكهرباء / BSOD:** دورة **Durable Checkpoint** (`FlushFileBuffers` أولاً ← ثم `SQLite COMMIT` + `.vortex.meta` ذري) كل **20 ثانية** (قابلة للضبط 15–30s) **وإلزامياً** عند `Pause`، و`Graceful Shutdown` (`WM_QUERYENDSESSION`)، والاكتمال `100%`.
2. **`FlushFileBuffers` كل ثانيتين / 32 MiB** — عنيف جداً على القرص ويخلق عنق زجاجة للسرعات العالية.
3. **عدم استدعاء `FlushFileBuffers` إطلاقاً** — يعرّض الملف للتلف الصامت عند انقطاع الكهرباء المفاجئ.

## Decision
اعتماد **نموذج المتانة ثنائي المستوى بدورة Checkpoint كل 20 ثانية** (وعند الإيقاف والإغلاق والاكتمال)، مع خوارزمية `If-Range` المتوافقة مع RFC 9110 (رفض إرسال Weak ETag `W/"..."` في `If-Range`).

## Consequences
- **إيجابيات:** أقصى سرعة قرص ممكنة، حماية عمر SSD، وصحة ملفات مضمونة 100% (أقصى ما يُعاد تحميله عند انقطاع الكهرباء هو آخر ≤ 20 ثانية).
- **سلبيات ومقايضات:** يتطلب التزاماً صارماً بعدم تحديث جدول `segments` في SQLite إلا بعد نجاح `FlushFileBuffers`.
- **التحقق والفرض:** اختبارات Failpoints بين `Flush` و`COMMIT` + اختبار تعذيب 100× `kill -9` + مطابقة SHA-256.
